    stacs.receipt¶

    Provenance receipts for catalogue items: crate's receipt contract, in Python.

    A receipt is one record per published output -- output (what it is), recipe (how it was made), result (what came out) and context (where and when) -- with a recipe_id that identifies the recipe alone. Two items with the same recipe_id were made the same way, so a rebuilt item can be told apart from a changed one.

    What this module does and does not do. The builder hands it values; it computes the ids, writes the receipt and compares two of them. It reads no source data and builds no item, which is why it belongs in a package that works on a catalogue after its items exist.

    Its canonical form is frozen, which stacs.verify's is not. verify.canonical_json may change shape with no migration, because nothing stores a body digest -- both sides are recomputed every run. A recipe_id is published, inside items and beside them, so the bytes it is taken over can move only with a new receipt schema version. The two forms are also different on purpose: verify's drops links and null members to absorb what pgstac's round trip changes, and a receipt's applies no STAC rules at all. Neither may be used for the other.

    The contract is crate's, vendored under data/receipt/ at a pinned tag and checked against it in CI; crate's test vectors are the only thing keeping the two implementations in step.

    ReceiptError ¶

    Bases: ValueError

    A receipt, recipe or table that has no canonical form, or does not meet the contract.

    Raised with what was wrong and where, never with the value alone: a message naming the column or the member is the difference between a two-minute fix and a bisect.

    Difference dataclass ¶

    One field that differs, with the action the register gives it.

    side is the block the register pattern starts in, not a judgement about which receipt is wrong.

    Comparison dataclass ¶

    The outcome of comparing two receipts.

    differences is an ORDERED LIST and may repeat a field: a collection with two keys missing reports its own path twice, which crate's a migrated receipt vector shows for both recipe.inputs and recipe.config.settings. A set would lose one of each.

    fields property ¶

    [(field, action)] -- what crate's vectors pin, without the prose detail.

    ItemVerdict dataclass ¶

    What a receipt says about one item whose published and served bodies differ.

    • same: every mirrored field agrees on both sides and with the receipt, so whatever changed in the body is outside what the receipt describes -- a bbox correction, a link.
    • rebuilt: the recipe is the same on both sides and a result field moved, so the item was built again from the same inputs.
    • changed: the recipe itself differs between the two sides.
    • inconsistent: the item's provenance could not be established -- it disagrees with the receipt it links, that receipt could not be read, or it links none at all. One category because they have one consequence; the notes say which it was. Never reported as agreement.

    ok property ¶

    same is the only verdict that is not drift on this axis.

    load_json(text) ¶

    Parse JSON the way the receipt contract requires: every number as a double.

    JSON has one number type and RFC 8785 spells every number as ECMAScript does, but Python's json reads an integer literal as int -- and rfc8785 refuses an int past 2^53 rather than rounding it. So this is the one reader every entry point here uses, rather than a parse_int= argument repeated at each call site and forgotten at one of them.

    Examples:

    >>> load_json('{"n": 1152921504606846976}')["n"]
1.152921504606847e+18
>>> load_json('{"n": 3}')["n"]
3.0
>>> canonical(load_json('{"n": 1152921504606846976}'))
b'{"n":1152921504606847000}'

    canonical(value) ¶

    RFC 8785 (JCS) canonical JSON of value, with no STAC rules applied.

    This is the plain canonical form crate's specification names: nothing is removed and nothing is absorbed. stacs.verify.canonical_json is a different function for a different job -- it drops links and null members because pgstac does -- and the two must not be substituted for one another.

    Examples:

    Keys sorted, nulls kept, 1.0 written as 1, -0 as 0:

    >>> canonical({"b": None, "a": 1.0, "c": -0.0})
b'{"a":1,"b":null,"c":0}'

    A top-level scalar is a JSON document too:

    >>> canonical("x")
b'"x"'

    No canonical form is an error, naming the member:

    >>> canonical({"n": float("nan")})
Traceback (most recent call last):
...
stacs.receipt.ReceiptError: no canonical form at n: ...

    recipe_id(recipe) ¶

    SHA-256, lowercase hex, over the canonical JSON of a recipe block without its own recipe_id.

    The whole recipe and nothing else: output, result and context are not part of it, and neither is any input's result -- an input enters by its own identity (recipe_id, version_id, sha256, or a declared none).

    Examples:

    The empty recipe, which crate's vectors pin:

    >>> empty = {"code": {}, "config": {"files": {}, "settings": {}},
...          "inputs": {}, "seed": None}
>>> recipe_id(empty)
'ecb53cd4e03b09490f6c581b1195aa9635e5fff51790d64e19d2a2a79f8a0493'

    A recipe carrying an id hashes as though it did not:

    >>> recipe_id({**empty, "recipe_id": "0" * 64}) == recipe_id(empty)
True

    A keyed collection written as a list is refused, not hashed:

    >>> recipe_id({**empty, "inputs": ["network"]})
Traceback (most recent call last):
...
stacs.receipt.ReceiptError: recipe.inputs must be an object keyed by name, got list: ...

    tolerance_decimals(tol) ¶

    The decimals a tolerance rounds to.

    A tolerance is an absolute power of ten from 1 to 1e-15, so it names both the rounding of a fingerprint and what a comparison accepts. Anything else has no rounding that matches it.

    Examples:

    >>> tolerance_decimals(1e-9)
9
>>> tolerance_decimals(1)
0
>>> tolerance_decimals(0.5)
Traceback (most recent call last):
...
stacs.receipt.ReceiptError: tolerance 0.5 is not a power of ten from 1 to 1e-15

    table_canonical(table, tolerance=None) ¶

    The bytes a table's fingerprint is taken over.

    table is column-major, {"columns": {<name>: {"type": <t>, "values": [...]}}}, with t one of character, integer, double, logical, date, datetime. tolerance maps a column name to a power of ten; a double in such a column is written with that many decimals, and without one it gets its shortest round-trip spelling.

    Columns sort by their UTF-8 bytes and so do rows -- by the bytes of each row's own JSON, not by their values, so ["a b"] sorts before ["a"] (a space is below the closing quote). The rule is mechanical so that no implementation needs a collation.

    Examples:

    >>> t = {"columns": {"n": {"type": "integer", "values": [2, 1]},
...                  "km": {"type": "double", "values": [7.25, 0.5]}}}
>>> table_canonical(t)
b'{"columns":["km","n"],"rows":[["0.5","1"],["7.25","2"]]}'
>>> table_canonical(t, {"km": 1})
b'{"columns":["km","n"],"rows":[["0","1"],["7","2"]]}'

    table_fingerprint(table, tolerance=None) ¶

    SHA-256, lowercase hex, of table_canonical(table, tolerance).

    Not to be confused with a schema fingerprint, which hashes a table's column names and types and never its values.

    Examples:

    >>> table_fingerprint({"columns": {"a": {"type": "integer", "values": []},
...                                "b": {"type": "integer", "values": []}}})
'4b50177c31441e4ae3e6691a6f82a75a30a21f197dd400e7a9a781c99eff4d36'

    double_from_bits(bits) ¶

    The double a 16-hex-digit big-endian bit pattern denotes.

    crate's vectors give every double as its bits, so no decimal parser stands between a vector and the value it fixes. A caller with a number does not need this.

    Examples:

    >>> double_from_bits("3e70000000000000")  # 2 ** -24
5.960464477539063e-08
>>> _shortest(double_from_bits("3e70000000000000"))
'5.960464477539063e-8'

    validate(receipt) ¶

    Check a receipt against the frozen schema. Returns None, raises on the first failures.

    Every error is collected and the message names the member paths, because a receipt that fails in three places usually fails for one reason and the paths are the diagnosis.

    The schema is the vendored copy, not the URL: the suite is offline, and a validator that fetched its schema would be checking whatever is served today against bytes that are supposed to be frozen. tools/crate_receipt_vendor.sh check is what compares the two.

    Examples:

    >>> validate({"output": {}})
Traceback (most recent call last):
...
stacs.receipt.ReceiptError: not a valid receipt: ...

    read(path) ¶

    Read a receipt file, refusing any version but the one this module implements.

    Refused rather than warned about, as crate's reader does: a later version may spell a field the same way and mean something else, and a comparison across two versions would report fields that agree as differing.

    reindent(data) ¶

    Canonical JSON re-indented at two spaces, with empty containers left collapsed.

    A text transformation, and that is the point: the file must carry the canonical number spellings, and re-serialising the parsed object does not. json.dumps writes 1e-06 where JCS writes 0.000001, and 1e-09 where JCS writes 1e-9 -- and crate's own worked-case receipt holds both of those as ordinary tolerance values.

    Examples:

    >>> print(reindent(b'{"a":{},"b":[1,2],"c":{"d":1e-9}}'))
{
  "a": {},
  "b": [
    1,
    2
  ],
  "c": {
    "d": 1e-9
  }
}

    write(receipt, path, publish=True) ¶

    Write a receipt, computing its recipe_id, and return the SHA-256 of the bytes written.

    The caller supplies the values; the ids are computed here, so a builder cannot publish a recipe_id that does not match the recipe beside it. The receipt is validated before anything is written.

    publish drops context.host, which is the one member a published receipt leaves out rather than nulls: where a thing was built is not something an outside reader needs, and it is never part of an identity.

    The returned digest is what an item's receipt asset carries as file:checksum. Nothing else can compute it -- the receipt's own bytes are not inside it -- and without it a reader that fetches a receipt beside an item cannot tell it fetched that item's receipt.

    The caller's dict is not modified.

    register() ¶

    crate's register: every receipt field that can differ, and what a difference means.

    refuse makes the verdict different, warn and record never change it. Returned in file order, as a plain dict of field pattern to action.

    Examples:

    >>> register()["recipe.seed"]
'refuse'
>>> register()["context.time"]
'record'
>>> sorted(set(register().values()))
['record', 'refuse', 'warn']

    compare(a, b, overrides=None) ¶

    Compare two receipts: identical, equivalent or different, and what differed.

    Any refuse makes it different; failing that, any within makes it equivalent; a warn or a record never changes the verdict, so two receipts that differ only in when and where they were built are identical with the difference still listed.

    overrides may change a field's action, under crate's rule: known fields only, an action of refuse, warn or record, and no recipe.* field -- every recipe field refuses because recipe_id covers it, and relaxing one would publish two different recipes as one.

    A null recipe_id on either side always refuses: a migrated receipt holds no recipe identity, so neither side can vouch for a recipe it does not have.

    Examples:

    >>> one = {"output": {}, "recipe": {}, "result": {}, "context": {"time": "t"}}
>>> compare(one, one).verdict
'identical'
>>> other = {**one, "context": {"time": "later"}}
>>> c = compare(one, other)
>>> c.verdict, c.fields
('identical', [('context.time', 'record')])
>>> compare(one, {**one, "recipe": {"seed": 1}}).verdict
'different'

    stac_fields(receipt, assets=None, receipt_asset=None, receipt_sha256=None) ¶

    The receipt's identity fields, as an item mirrors them.

    {"stac_extensions": [...], "properties": {...}, "assets": {...}}, for a builder to merge into the item it is writing. The receipt itself stays the full record; these exist so a STAC client or a pgstac queryable needs no second fetch.

    assets maps an asset key to its href relative to the item, which is what a part is keyed by. receipt_asset names the asset that links the receipt, and receipt_sha256 is the digest write returned for it -- nothing else can compute that one, because a receipt's own bytes are not inside it.

    A migrated receipt has no recipe identity (recipe_id null), so the field is left out rather than published as a null, which the field schema would refuse anyway.

    Examples:

    >>> r = {"output": {}, "recipe": {"recipe_id": "a" * 64,
...                               "code": {"stacs": {"version": "0.2.0"}}},
...      "result": {"parts": {"x.tif": {"sha256": "b" * 64, "bytes": 12}}},
...      "context": {"time": "2026-11-08T00:00:00Z"}}
>>> fields = stac_fields(r, assets={"data": "x.tif"})
>>> sorted(fields["properties"])
['processing:datetime', 'processing:software', 'receipt:recipe_id']
>>> fields["assets"]["data"]["file:size"]
12
>>> fields["assets"]["data"]["file:checksum"][:4]
'1220'

    receipt_asset(item) ¶

    The asset that links an item's receipt, or None.

    The contract is the asset link, not a filename: the receipt is published beside the item "as an asset with role metadata". A catalogue that publishes under a receipts/ prefix would break a receipt.json-beside-the-item assumption silently.

    THE ONE PRODUCER of that answer. receipt_href, item_problems and item_verdict all come through here, because they have to agree about which asset it is: a second loop that kept the LAST match instead of the first reported an item as inconsistent whenever it carried another metadata JSON asset -- a QA report, a legacy manifest -- and that is good input (round 1).

    The first match wins, and it must satisfy every condition: a non-empty href, role metadata, type application/json.

    receipt_href(item) ¶

    The href of the asset that links an item's receipt, or None.

    item_problems(item) ¶

    Everything wrong with an item's receipt fields, as a list of sentences.

    Collected rather than raised one at a time: an item is usually wrong in one way that shows up in three fields, and the set is the diagnosis. An empty list is the pass.

    Three layers, because no single one covers it:

    • the vendored field schema, which constrains stac_extensions, type and receipt:recipe_id and refuses any other receipt:-prefixed key;
    • the formats it cannot reach -- a file:checksum multihash and a processing:datetime -- because the file and processing schemas are fetched by URL and the suite is offline;
    • the links the contract requires: each extension whose fields are present, and the asset that carries the receipt.

    item_verdict(published, served, receipt, receipt_sha256=None) ¶

    Compare an item's published and served bodies through the receipt it links.

    receipt_sha256 is the digest of the receipt bytes as fetched. Given, it is checked against the published item's receipt asset, which is the only way to tell that the receipt read is the one the item claims -- a receipt fetched by a filename convention could belong to anything.

    The receipt is what makes this more than a field diff: an item whose mirrored fields do not match the receipt beside it is inconsistent whatever the two sides agree on.

    Examples:

    >>> item = {"properties": {"receipt:recipe_id": "a" * 64}}
>>> r = {"recipe": {"recipe_id": "a" * 64}, "result": {}, "context": {}, "output": {}}
>>> item_verdict(item, item, r).verdict
'same'
>>> moved = {"properties": {"receipt:recipe_id": "b" * 64}}
>>> item_verdict(item, moved, r).verdict
'changed'
